# Coding guidelines

The rules this codebase is held to, and which of them a machine enforces. If you
are reading a diff and wondering whether something is allowed, this is the
answer.

Most of these are invariants rather than preferences: breaking one is a bug even
if the tests pass. Where a rule is mechanically checked, the checker is named -
prefer adding a check to writing a paragraph.

## Cryptographic invariants

**All asymmetric cryptography is post-quantum.** ML-KEM-768 (FIPS 203) for key
establishment, ML-DSA-65 (FIPS 204) for identity and authentication. RSA, ECDH,
X25519, Ed25519 and ECDSA must not appear in an application code path. This is
the project's whole reason to exist, so it is enforced rather than trusted:
`scripts/audit.py` greps for them and CI fails the build.

The one deliberate exception is the benchmark suite, which needs a classical
baseline to measure against. It lives behind a dynamic import in
`client/src/bench/` and is excluded from the audit by path, so it can never be
reached from application code.

**Primitives are composed, never implemented.** Client cryptography comes from
`@noble/post-quantum`, `@noble/ciphers` and `@noble/hashes` and nothing else;
the server uses `cryptography` (pyca/OpenSSL) and `argon2-cffi`. Do not hand-roll
a construction, and do not add a fourth client crypto dependency without a
written justification in the commit message.

**The fixed scheme.** KDF is HKDF-SHA-512. AEAD is XChaCha20-Poly1305 with a
24-byte random nonce, never reused under one key. Hash is SHA-512. Passphrase
stretching is Argon2id at m = 65536 KiB, t = 3, p = 1; those parameters are
stored beside the ciphertext so they can be raised later, and the server refuses
to boot in production if its live hasher has drifted from them.

**Randomness** comes from `crypto.getRandomValues` on the client and `secrets` /
`os.urandom` on the server. `Math.random` and Python's `random` are banned and
grepped for.

**The server is a relay, and knows nothing.** It must never see plaintext, a
private key, or a symmetric key. Every message envelope is an opaque blob it
routes on a recipient column and never parses. If a server-side feature seems to
need any of that, the design is wrong - stop and reconsider rather than reaching
for the plaintext.

## Code rules

- TypeScript runs `strict` with `noUncheckedIndexedAccess` and
  `exactOptionalPropertyTypes`. Python is fully type-hinted and `mypy --strict`
  clean. Neither is negotiable per-file.
- No `eval`, `new Function`, `innerHTML`, `outerHTML`, `document.write`, `exec`,
  or `pickle` on untrusted input. Grepped by `scripts/audit.py`.
- The session token lives in JavaScript memory only. It is never written to
  `localStorage`, `sessionStorage`, or a cookie - the audit greps for that too.
- Every server input crosses a Pydantic model with `extra="forbid"`. Every
  client-bound string is rendered as terminal text, never as markup.
- Errors are uniform in shape and timing class. No stack traces reach a client,
  and no response distinguishes "no such user" from "wrong signature" - that
  distinction is an enumeration oracle.
- Dependencies are pinned exactly, lockfiles committed. An addition needs a
  reason in the commit message.
- User-facing failures carry a stable `[E###]` code from
  `client/src/terminal/messages.ts`, documented in [MESSAGES.md](MESSAGES.md). A
  drift test fails the build if the two disagree.

## Async discipline (client)

The executor runs several independent lanes: a command lane, a render lane for
view rebuilds, and a WebSocket receive chain. They mutate shared ratchet and
store state, so a dropped promise is a lost state write rather than a cosmetic
bug. `@typescript-eslint/no-floating-promises` is an error; if you genuinely
want fire-and-forget, write `void` and mean it.

Ratchet state is persisted write-ahead - advanced and saved *before* the send it
belongs to - so a failed send can never reuse a message key.

## Tests

Every behavioural change ships with its tests. Beyond that:

- Cryptographic code is tested for its security property, not just its happy
  path: forward secrecy, post-compromise recovery, out-of-order delivery, and
  tamper rejection each have explicit tests.
- The command parser has a fuzz test: random bytes and mutated valid commands
  must never throw uncaught and never execute an unlisted command.
- Client primitives are checked against `shared/vectors/`, generated by an
  independent implementation the client shares no code with.
- Prefer a test that would have caught the bug over a comment describing it.

## What CI enforces

All of the following block a merge:

| Gate | Command |
|---|---|
| Crypto and injection greps | `python scripts/audit.py` |
| Client lint | `npm run lint` (ESLint, type-aware) |
| Client types | `npm run typecheck` |
| Client tests | `npm test` |
| Client dependencies | `npm audit --audit-level=high` |
| Server lint | `ruff check .` (includes bandit security rules) |
| Server types | `mypy --strict app` |
| Server tests | `pytest -q` |
| Server dependencies | `pip-audit` |

Run them locally before pushing; `scripts/dev/diagnose.ps1` checks the toolchain
those commands need.

## Honest limitations

Stated here so nobody has to rediscover them, and so no one claims otherwise:

- A cross-site scripting bug means key theft despite the CSP. WebCrypto has no
  ML-KEM or ML-DSA, so key material must live in JavaScript memory. CSP is a
  mitigation, not a cure.
- Timing side channels are plausible on any web platform.
- Deleting from IndexedDB is not forensic erasure, and peer-side deletion is
  cooperative: it relies on the other client honouring the request, and cannot
  reach a screenshot.
- Rate limiting is the only denial-of-service defence, and the in-process
  limiter resets on restart. See [deploy/rate-limiting.md](deploy/rate-limiting.md).
